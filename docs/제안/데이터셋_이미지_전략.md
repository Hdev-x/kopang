> 상품 목업 데이터, ML 데이터셋, 상품 이미지 처리 방식에 대한 논의 정리.
> 스택: **Spring Boot + MyBatis + PostgreSQL** / ML 목표: **고객 이탈(churn) 예측**
> 상태: 제안 (아직 미구현)

## 1. 카테고리 분류 구조

현재 정리된 카테고리: **대분류 13개 / 중분류 93개** (Notion "웹" 페이지 기준).

### 단계 수 결정
| 방식 | 장점 | 단점 | 추천 |
|------|------|------|------|
| 2단계 (대 > 중) | 단순, 4주 프로젝트에 충분 | 실제 쇼핑몰보다 얕음 | ✅ MVP |
| 3단계 (대 > 중 > 소) | 쿠팡스러움, 필터 풍부 | 데이터·화면 작업 증가 | 여유 시 |

> 중분류 예시 품목( ) 안 항목(러닝화, 토너 등)이 사실상 **소분류 후보**.

### DB 설계 — 자기참조 테이블 (단계 수 무관)
```sql
CREATE TABLE category (
  id          BIGSERIAL PRIMARY KEY,
  parent_id   BIGINT REFERENCES category(id),  -- NULL이면 대분류
  name        VARCHAR(50) NOT NULL,
  depth       SMALLINT NOT NULL,               -- 1=대, 2=중, 3=소
  sort_order  INT DEFAULT 0
);
```
- `parent_id`만 채우면 2단계든 3단계든 동일 스키마.
- 소분류는 나중에 **row만 추가**하면 되므로 스키마 변경 불필요.
- **결정 사항(TODO): 2단계 vs 3단계** — 우선 대/중까지 적재, 소분류는 여유 시.

## 2. 두 종류의 데이터셋 (성격이 다름)

### (A) 상품 목업 데이터 — "보여주기용"
- 목적: 화면에 상품을 채우기 위한 데모 데이터. **양 자체는 중요하지 않음.**
- 규모: 카테고리당 10~30개 → **총 1,000~3,000개** (욕심내도 1만 개).
- 생성: Python + `Faker` → CSV → PostgreSQL `COPY` 적재.
- 필드 예: 상품명, 가격, 재고, category_id, 이미지 URL, 평점 등.

### (B) ML 데이터셋 — "이탈 예측용" (핵심, 난이도 높음)
- 상품 데이터가 **아니라**, 고객의 **시간에 따른 행동 로그 + 이탈 라벨**.
- 필요한 테이블(대략):
  - `users` — 가입일, 등급
  - `orders` / `order_items` — 주문 이력 (날짜 중요)
  - `cart_events` — 장바구니 담기/방치 (위험군 1번)
  - `subscriptions` — 구독/해지 (위험군 6번)
  - `user_activity` — 로그인/조회 로그
- **핵심: 랜덤 생성 금지.** 패턴을 심어서 **시뮬레이션**해야 함.
  - 예) "장바구니 담고 3일+ 주문 없음" → 이탈 라벨 1
  - 예) "평균 구매주기 ×1.5 경과" → 리필 대상
  - 정상 유저는 꾸준히 주문
- 그냥 랜덤이면 패턴이 없어 ML 학습이 무의미해짐.

## 3. PostgreSQL 용량 — 걱정 없음

| 데이터 | 행 수(대략) | 용량(대략) |
|--------|------|-----------|
| 상품 | 3,000 ~ 10,000 | ~5 MB |
| 유저 | 5,000 | ~1 MB |
| 주문 + 주문상품 | ~17만 | ~30 MB |
| 행동 로그 | ~50만 | ~100 MB |
| **합계** | **~70만 행** | **~150 MB** |

- PostgreSQL은 단일 테이블 **수억~수십억 행**도 처리.
- 유저 10배(5만) → 700만 행 / ~1.5GB여도 노트북에서 문제없음.
- **진짜 병목은 용량이 아니라 쿼리 설계.** 이탈 분석 쿼리(윈도우 함수 등)에 **인덱스**를 제대로 거는 게 성능 좌우 → 프로젝트 목표("쿼리 튜닝")와 직결.

## 4. 상품 이미지 전략

### 원칙
> **이미지 파일 자체를 DB에 넣지 말 것.** DB엔 **경로(URL)만 문자열로** 저장, 실제 파일은 외부.
- `BYTEA`(BLOB)로 박으면 DB가 수백 MB~GB로 불어나 백업·쿼리가 느려짐.

```sql
-- product 테이블엔 경로만
thumbnail_url  VARCHAR(255),   -- 대표 이미지 1장

-- 여러 장이면 별도 테이블
CREATE TABLE product_image (
  id          BIGSERIAL PRIMARY KEY,
  product_id  BIGINT REFERENCES product(id),
  image_url   VARCHAR(255) NOT NULL,
  sort_order  INT DEFAULT 0
);
```

### 파일 호스팅 선택지
| 방식 | 내용 | 난이도 | 추천 |
|------|------|:---:|:---:|
| 플레이스홀더 URL | picsum / placehold.co 등 외부 더미 | 매우 쉬움 | ✅ 목업 |
| 정적 폴더 서빙 | `resources/static/images/`, DB엔 `/images/123.jpg` | 쉬움 | 실물감 필요시 |
| 클라우드(S3 등) | 실제 서비스 방식, 업로드 기능 포함 | 중간 | 시간 남으면 |

### "상품과 관련된 이미지"로 채우기
관련성 있는 이미지를 넣고 싶을 때 3가지:

| 방법 | 관련성 | 고유성 | 방식 |
|------|:---:|:---:|------|
| ① 키워드 이미지 서비스 | 중~상 | 높음 | 카테고리 키워드로 매번 다른 사진 |
| ② 진짜 상품 API | 매우 높음 | 낮음(수 제한) | 이름·가격·이미지 세트 일치 (DummyJSON, FakeStoreAPI) |
| ③ 카테고리별 큐레이션 풀 | 높음 | 낮음 | 분류당 사진 5~10장 미리 받아 재사용 |

#### 채택 방향: ① 키워드 기반 (loremflickr)
```
https://loremflickr.com/400/400/sneaker?lock={product_id}
```
- 카테고리를 키워드로 넘기면 대충 맞는 이미지가 상품마다 다르게 나옴.
- `lock={product_id}` → 상품별 고유 이미지 고정(새로고침해도 안 바뀜).

**한계 (인지 필요):**
- 키워드는 **영어**여야 함 → 한글 분류 → 영어 키워드 **매핑표** 필요.
- 키워드당 풀이 수십~수백 장 → 같은 중분류 20~30개부터 **사진 반복**.
  - 완화: 중분류 1개에 키워드 **2~3개** 섞기 (운동화 → `sneaker`, `running shoes`, `trainers`).
- Flickr 일반 사진이라 **흰 배경 상품컷이 아님** (감성/일상 사진 느낌).
- (참고: 예전 `source.unsplash.com` 키워드 방식은 2024년 종료.)

#### 결론
- "화면이 다양하게 채워진다" → **① 만으로 충분** ✅
- "진짜 쇼핑몰 상품컷처럼 깔끔" → ① 부족 → 메인 노출(배너·추천 상품 몇 개)만 ②/③로 보강.
- ML이 진짜 목표이므로 **이미지엔 시간 최소화**: ①로 전체 깔고 시간 남으면 메인만 다듬기.

## 5. 추천 진행 순서

1. `category` 테이블 + 대/중분류 데이터 적재 (현 93개 활용)
2. `Faker`로 상품 목업 1,000~3,000개 적재 (+ loremflickr 이미지 URL 자동 채움)
3. **시뮬레이션 스크립트**로 유저 행동 로그 + 이탈 라벨 생성 ← ML 핵심
4. 이탈 분석 쿼리에 인덱스 → 튜닝
