# Copang 이탈(Churn) 방식 — 룰 기반 + ML 학습층

> ⚠️ **확정 아님 — 회의 논의용.** 전제: "프로젝트로 *배우면서* 한다" (수업 들은 범위 기반)
> 팀 ML 역량은 낮음(수업 다수 결석) → **"의도된 학습 도전 + 안 망하는 안전망"** 구조로 간다.

---

## 0. 큰 원칙
- **주제 = 고객 이탈 방지.** churn이 메인이므로 ML도 churn에 쓰는 게 가장 정합적.
- **학습이 프로젝트 목적의 일부** → ML을 피하지 않고 *정면으로 한 번* 도전한다.
- 단, **"배운다 ≠ 프로젝트를 도박에 건다".** ML이 안 끝나도 데모는 돌아가야 함.
- **새 학습 도전은 ML 하나만.** 나머지(커머스/인증/프론트)는 배운 것 안에서 안정적으로.

## 1. 2층 구조

### 🔴 바닥층 — 룰 기반 churn (P0, 무조건 동작)
README대로 SQL/배치 로직. ML 없이 백엔드 역량만으로 동작 + **ML 학습용 라벨/데이터까지 생성.**

| 위험군 | 판단 기준 | 대응 | 데이터 출처 |
|---|---|---|---|
| 1. 장바구니 방치 | 담은 뒤 3일간 주문 없음 | 리마인더 | `cart_items.created_at` |
| 6. 구독 해지 | 해지 버튼 클릭 | 록인 모달 | `memberships.cancelled_at` |
| 8. 주기성 단절 | 평균 구매주기 ×1.5 경과 | 리필 알림 | `orders.ordered_at` (윈도우 함수) |

→ 감지 결과는 `risk_flags` 테이블에 기록, 대응은 `coupons`/`notifications`로.

### 🟠 학습 목표층 — ML 이탈 예측 (P1, 도전)
룰 위에 분류 모델을 얹어 **"이탈 확률 점수"** 제공. 룰은 단일 조건, ML은 다변량 패턴.

```
합성 유저 행동데이터 생성 (전처리)
  → 룰로 라벨링 (이탈 1 / 잔존 0)
  → 로지스틱 회귀로 이탈 확률 학습
  → 모델 저장 (joblib)
  → FastAPI로 예측 API 서빙
  → Spring이 WebClient로 호출 → risk_flags에 점수 기록
```

## 2. 수업 노트 매핑 (relearning 교재 = 이미 있음)

| 단계 | 참고 노트 | 비고 |
|---|---|---|
| 데이터 전처리/EDA | 01 | 합성 데이터 정제 |
| 이진 분류(로지스틱 회귀) | 02 (유방암 악성/양성) | **이탈/잔존 = 동일 구조** |
| 모델 저장/예측 전처리 | 04 (joblib, reindex, transform) | 저장→신규예측 |
| FastAPI 서빙 + Spring 연동 | 05 (WebClient) | 422·파싱 트러블슈팅 이미 해결됨 |
| FastAPI ↔ PostgreSQL | FastAPI+Psycopg2 | ML 서버가 DB 직접 read |

## 3. ⚠️ 함정과 완화
- **순환 라벨 함정**: 룰로 라벨 만들고 그 라벨로 학습하면 모델이 룰을 그대로 외움 = ML 의미 없음.
  - **완화**: 피처를 룰 하나보다 풍부하게 (접속빈도, 총구매액, 카테고리 다양성, 평균 구매주기 등).
    → 모델이 "단일 조건"이 아니라 "신호 조합"으로 학습. 발표 차별화 포인트.
- **이해 못 한 ML = 시한폭탄 + 면접 마이너스**: "돌긴 도는데 뭔지 모름"은 금지. 오너가 발표에서 설명 가능한 수준까지 이해하는 게 학습 성과.

## 3-1. 데이터셋 — 합성 데이터 (CSV 먼저, DB 시드 나중)
실제 유저 데이터 없음 → **합성 데이터 직접 생성.** (Kaggle 등 공개셋은 통신사 등 도메인이 안 맞아 제외)

**진행 순서 (확정)**
1. **지금**: `ml/generate_churn_data.py` → `ml/churn_dataset.csv` (학습용)
   - 스키마 안 타서 **ML 학습 바로 착수 가능** / 기본 4000명 / 의존성 `pandas`, `numpy`
2. **스키마 확정(월요일~) 후**: DB 시드 추가
   - **같은 생성 로직**에서 뽑아 *학습 피처 = 앱이 계산하는 피처* 정합성 유지

**피처 (유저 1명 = 1행)**
```
recency_days, order_count_30d, total_spend, cart_abandon_count,
cycle_ratio, category_diversity, is_member, tenure_days  → churned(0/1)
```

**라벨 설계 (순환 함정 완화)**
- 이탈 라벨 = **여러 피처의 확률적 함수 + 노이즈** (단일 규칙으로 박지 않음)
  → 모델이 "단일 조건"이 아니라 "신호 조합 패턴"을 학습

**DB 시드가 주는 것 (나중)**: 앱 화면 데이터로 채움 / 룰 배치 실제 동작 확인 / ML end-to-end 시연 / 학습·서빙 정합성

## 4. 안 망하게 하는 안전장치
1. **룰 기반을 먼저 완성** → 데모는 룰만으로 완전히 돌아감 (ML에 운명 걸지 않음)
2. **타임박스**: 2주차 끝까지 ML 안 붙으면 **동결하고 룰로 발표**
3. **ML 오너 1명**: 팀 전체 기대 X, 그나마 관심 있는/여유 있는 한 명이 격리 모듈로
4. **fallback**: ML 호출 실패 시 룰 결과로 자동 대체

## 5. 아키텍처 선택지 (회의에서 결정)
- **(A) FastAPI가 DB 직접 read (Psycopg2)** — 배치로 전체 유저 스코어링. *주기적 대량 처리*에 자연스러움. **추천**
- (B) Spring이 데이터 담아 FastAPI 호출 (WebClient) — 실시간 단건에 적합
- 혼합: 배치는 A, 즉시조회는 B
