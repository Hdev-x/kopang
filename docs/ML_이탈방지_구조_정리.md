```
①예측 ──▶ ②대응 ──▶ ③측정 ──▶ ④대시보드 ──▶ 관리자가 다음 액션 결정

```

핵심: 관리자/판매자가 대시보드로 **"우리 대응이 먹혔나"** 를 보고 다음 행동을 정한다.

## 2. ML 두 개 + 룰 한 개 (역할 분담)

| 무엇 | 방식 | 도구 | 역할 |
|---|---|---|---|
| **이탈 예측** | 로지스틱 회귀(분류) | scikit-learn | **누가** 떠날지 (확률) |
| **맞춤 상품 추천** | item 기반 협업필터링 | pandas / numpy | **뭘** 보여줄지 = 이탈 **대응 무기** |
| 비슷한 상품 | 룰 (카테고리/가격) | SQL | ML 아님 |

→ 추천이 "위험 고객 리텐션 추천"으로 쓰여서, 클릭 → 주문 → 수익전환이 ③에서 측정된다.

## 3. 2층 구조 (룰 + ML)

```
사용자 행동 데이터
   ├─ 룰 층(SQL)  ──▶ 위험 "유형" 감지: 장바구니방치 / 주기단절 / 멤버십해지   ← 왜 위험 (안전망)
   └─ ML 층       ──▶ 이탈 확률 0~1 ──▶ "등급" 고/중/저                      ← 얼마나 위험
```

- **룰 층** = ML 없어도 도는 바닥(데모 안전망) + ML 학습용 라벨/데이터 생성
- **ML 층** = 여러 신호를 조합해 확률 산출

> 룰 = 사람이 IF 조건 박음(확실·단순) / ML = 데이터로 학습(확률·다변량). 둘을 겹쳐 쓴다.

---

## 4. 위험 분류 두 축 (헷갈리지 않게)

같은 고객을 **두 각도**로 본다.

| 축 | 값 | 의미 | 어디에 |
|---|---|---|---|
| **유형 (룰)** | 장바구니방치 / 주기단절 / 멤버십해지 | **왜** 위험 → 대응 결정 | 상세·위험 고객 목록 |
| **등급 (ML)** | 고 / 중 / 저위험 | **얼마나** 위험 → 우선순위 | 요약 카드·대시보드 도넛 |

> 예) 김민수 = `멤버십 해지(유형)` + `0.87 고위험(등급)` — 둘 다 동시에 가짐.

## 5. 추적할 사용자 행동

| 역할 | 행동 |
|---|---|
| **① 이탈 신호 (예측 입력)** | 조회 · 구매 · 장바구니 · 찜 · 로그인 · 멤버십해지 (+ 검색 · 리뷰 · 주문취소 보조) |
| **② 대응 반응 (효과 측정)** | **쿠폰 사용 · 알림 클릭 · 추천 클릭** |

> ②가 없으면 대시보드 "효과 섹션(전환율·순효과)"이 빈칸이 된다. → 이벤트 로그로 남겨야 함.

---

## 6. 위험 유형별 감지 방법

| 유형 | 감지 기준 | 데이터 출처 |
|---|---|---|
| 장바구니 방치 | 담은 뒤 3일간 주문 없음 | `cart_item.created_at` + `orders` |
| 멤버십 해지 | 해지 버튼 클릭 / 상태 CANCELLED | `user_membership.status`, `cancelled_at` |
| 🟡 주기 단절 | 마지막 주문 후 (평균 구매주기 × 1.5) 경과 | `orders.ordered_at` (윈도우 함수 LAG) |

**🟡 주기 단절 — 단순 버전 유지 제안**

- 제안: **완전 삭제 대신 단순화해서 유지.**
  - 우리는 데이터를 합성으로 만드니 **주문 이력을 여러 건 깔아 "주기가 보이게" 시드 가능** → ①번 문제 거의 없음.
  - 단 **카테고리별 주기까진 안 감.** 전체 평균 주기 × 1.5, 과거 구매 2회 이상만 대상.
  - 정 빼려면 → 독립 위험군에서만 빼고 **ML 입력 피처(구매주기비율)로는 살리는** 방법도 있음.

## 7. 데이터셋 — 만들어서 돌리는 흐름

실데이터 없음 → 직접 **합성**. 단, 순환 라벨 함정을 피해야 한다.

### 7-1. 데이터는 두 종류다 (핵심)

| | A. ML 학습용 데이터셋 | B. 앱 DB 시드 데이터 |
|---|---|---|
| 형태 | **유저 1명 = 1행** (피처 표, CSV) | 실제 테이블(orders, cart_item…)에 row |
| 누가 읽음 | ML 모델 학습 | **룰 층(SQL) + 화면(대시보드)** |

### 7-2. 위험 "유형"은 앱 DB(B)에 이벤트로 심는다

유형은 글자로 박는 게 아니라, 그 상황을 만드는 **실제 row**를 심어 룰이 잡게 한다.

```
장바구니 방치 → cart_item에 3일 전 created_at row, 이후 orders 없음
주기 단절    → orders 여러 건 + 마지막 주문이 평균주기 × 1.5 이전
멤버십 해지   → user_membership.status = CANCELLED, cancelled_at 심음
```

### 7-3. ML 표(A)에는 "유형 이름"이 아니라 "수치 피처"로 들어간다

| 유형/신호 | ML 피처(수치) |
|---|---|
| 장바구니 방치 | `cart_abandon_count` |
| 주기 단절 | `cycle_ratio` |
| 멤버십 해지 | `is_member` |
| 접속 뜸 | `recency_days` |

> 모델은 "방치/단절/해지" 라벨을 보는 게 아니라, **숫자 조합**을 보고 이탈 확률을 학습한다.

### 7-4. 구체 예 — 가상 유저 "김민수"

```
[앱 DB(B)에 심는 것]
  orders:          1/1, 1/15, 1/29  (평균 14일주기, 오늘 3/1 → 31일 경과 = 주기단절)
  user_membership: CANCELLED, 2/20  (해지)
  last_login_at:   2/10            (20일 전, 접속 뜸)
        │ 같은 데이터를 SQL로 집계 ▼
[ML 표(A) 한 행]
  recency=20, order_count=3, cycle_ratio=2.2, is_member=0 … → churned=1 (확률+노이즈로 찍음)
```

### 7-5. 순환 라벨 함정 회피

- ❌ 라벨 = 단일 룰(`IF 30일 접속없음 THEN 이탈`) → 모델이 그 룰만 외움 = 무의미
- ✅ 라벨 = **여러 피처의 확률적 조합 + 노이즈** → 모델이 신호 조합을 *데이터로부터* 학습
  - 정확도 100% 안 나옴(현실적) / "ML이 단일 룰보다 낫다"는 비교가 가능

### 7-6. 두 가지 생성 방식

1. **분리형 (쉬움)**: ML CSV(A) 피처를 직접 생성 + 앱 DB(B) 따로 시드 → 빨리 착수, 둘이 어긋날 위험
2. **일원화 (정합성)**: 앱 DB(B) 이벤트 심고 → **같은 SQL로 집계해서** ML CSV(A) 생성 → 학습 피처 = 앱이 계산하는 피처
- **추천**: 처음엔 1번으로 ML 빨리 돌려보고, 데모 붙일 땐 2번으로 정합성 맞추기.

### 7-7. 돌리는 전체 흐름

```
1. 합성데이터 생성   generate_data.py  (유저별 피처 + 노이즈 라벨, 앱 DB 시드)
2. 학습             train_churn.py (sklearn .fit) / train_recommend.py (pivot + 코사인유사도)
3. 저장             joblib (모델 파일)
4. 서빙             FastAPI — /predict, /recommend
5. 배치 스코어링     전체 유저 예측 → DB 저장(churn_score, recommendation_history)
6. 화면             대시보드는 DB만 읽음 (실시간 추론 X)
```

> **이 프로젝트가 증명하는 것** = 데이터→학습→서빙→대응→측정 **파이프라인 + 시스템 통합**, 그리고 ML이 단일 룰보다 다변량 패턴을 더 잘 잡는다는 점.
> **한계(정직하게 명시)**: 합성 데이터라 *실제 고객* 예측 성능을 증명하지는 못함.

## 8. 아키텍처 (3-tier)

```
React (FE) ──JSON──▶ Spring Boot (BE, MyBatis + PostgreSQL) ──WebClient──▶ FastAPI (ML)
  대시보드/화면              결과 DB 저장 ◀──────────────────────── 이탈예측 + 추천
```

- FastAPI 한 대에 모델 2개(`APIRouter`로 분리) · 배치 스코어링 결과를 DB에 저장 후 화면은 읽기만
