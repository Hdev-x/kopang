## 1. 결론

Web 고객 화면에서 확인됐던 카테고리 빈 아이콘, 마이페이지 공용 목업, 주문·결제 shell, 고객지원 설명형 shell을 실제 화면 구조와 API 흐름으로 교체했다.

발표에서 사용하는 주요 Web 진입 경로는 모두 실행 서버에서 HTTP 200 응답을 확인했고, `frontend/src/web` 전체 ESLint와 production build가 통과했다.

다만 Web 주문서가 실제 UI·PG 경로에 연결됐다는 것과 주문 Backend의 금액·배송지 보안 정합성이 해결됐다는 것은 별개다. 서버 재계산과 배송지 snapshot은 팀 담당 필수 수정으로 남아 있다.

## 7. 팀원 발표 전 필수 수정

Web 고객 화면 구현은 이번 branch에서 보강했지만, 실제 주문·PG·멤버십 정책과 Backend 무결성은 각 담당자의 수정이 필요하다.

### 세민 — 상품·주문·결제·배송·리뷰

발표 전 우선순위:

1. 주문 금액·쿠폰·포인트를 Backend에서 다시 계산
2. 주문 당시 배송지 snapshot 저장
3. PG 승인·실패·재시도·취소 상태 정합성
4. 결제 버튼 중복 제출과 중복 주문 생성 방지
5. 배송완료·구매확정·리뷰 작성·포인트 지급 흐름 검증

완료 기준:

- Client가 전달한 최종 금액을 서버가 그대로 신뢰하지 않는다.
- 주문 상세에서 결제 당시 배송지를 확인할 수 있다.
- PG 승인 실패 후 주문 상태와 포인트·쿠폰이 어긋나지 않는다.
- 동일 주문이 중복 승인되거나 리뷰 포인트가 반복 적립되지 않는다.

### 태준 — 회원·인증·멤버십·쿠폰·포인트

발표 전 우선순위:

1. 멤버십 해지 예약 기간의 혜택 유지 정책 통일
2. 발표 고객·관리자 계정 role과 로그인 상태 확인
3. 쿠폰 소유권·중복 발급·포인트 사용 검증
4. 공개 발표 환경의 관리자·배치 API 최소 인증 경계 확인
5. 챗봇 fallback과 발표 설명 범위 일치

완료 기준:

- `CANCELLED` 예약 상태에서 `endDate` 전 혜택 여부가 화면·배송비·적립에서 동일하다.
- 일반 사용자가 관리자·배치 API를 호출할 수 없다.
- 쿠폰·포인트가 다른 사용자의 소유이거나 이미 사용된 상태라면 적용되지 않는다.
- 챗봇 장애 시 실제 동작과 발표 문구가 일치한다.

### 지호 — 고객지원·사용자 관점 통합 QA

발표 전 우선순위:

1. 회원가입부터 주문·배송·리뷰까지 전체 시나리오 수행
2. 일반 사용자·관리자 권한별 고객지원 API 확인
3. 공지·FAQ·Q&A·챗봇·알림의 빈 상태와 오류 상태 확인
4. 발표 동선별 실제 결과·기대 결과·스크린샷 기록
5. 발표 주 계정 실패에 대비한 백업 계정·주문 준비

완료 기준:

- 발표 시나리오를 중단 없이 처음부터 끝까지 수행한다.
- 발견 항목은 `화면/행동/기대/실제` 형식으로 담당자에게 전달한다.
- 발표용 주 계정과 백업 계정 모두 동일한 핵심 흐름을 수행할 수 있다.

### 팀 공통 결정
