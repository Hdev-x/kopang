# 목표 구조와 책임 경계

> 상태: 팀 합의 전 제안안

## 1. 목표

사용자용 mobile과 web은 UI/UX를 독립적으로 제작하되, 서버 통신과 핵심 업무 규칙은 공유한다. 관리자는 쇼핑 사용자 화면과 목적이 다르므로 별도 영역으로 유지한다.

## 2. 현재 구조

```text
src/
├─ api/
├─ components/
├─ hooks/
├─ lib/
├─ pages/
│  ├─ auth/
│  ├─ product/
│  ├─ cart/
│  ├─ order/
│  ├─ my/
│  ├─ notifications/
│  └─ admin/
├─ routes/
├─ styles/
└─ types/
```

현재 `pages/`와 사용자 `Layout`은 `--max-width: 480px`를 사용하는 mobile 중심 구현이다.

## 3. 최종 목표 구조

```text
src/
├─ shared/
│  ├─ api/                 # HTTP 요청 함수와 axios client
│  ├─ hooks/               # 인증·공통 server state 처리
│  ├─ lib/                 # format·validation·업무 규칙
│  ├─ types/               # API 요청·응답 타입
│  └─ components/          # 정말 동일한 primitive UI
│
├─ mobile/
│  ├─ layouts/
│  ├─ components/
│  ├─ pages/
│  └─ styles/
│
├─ web/
│  ├─ layouts/
│  ├─ components/
│  ├─ pages/
│  └─ styles/
│
├─ admin/
│  ├─ layouts/
│  ├─ components/
│  ├─ pages/
│  └─ styles/
│
├─ design-system/
│  ├─ foundations/
│  └─ components/
│
└─ routes/
   ├─ AppRouter.tsx
   ├─ MobileRoutes.tsx
   ├─ WebRoutes.tsx
   └─ AdminRoutes.tsx
```

이 구조는 최종 목표다. 첫 단계부터 모든 폴더를 한꺼번에 이동하지 않는다.

## 4. 영역별 책임

### shared

- API endpoint 호출
- 요청·응답 TypeScript type
- token 저장과 인증 상태
- 가격·날짜·상태 format
- 장바구니·주문·결제 등 공통 업무 규칙
- 화면 모양과 무관한 재사용 hook

`shared`에는 mobile/web 전용 className이나 layout 조건을 넣지 않는다.

### mobile

- 기존 사용자 화면의 초기 소유 영역
- mobile page JSX와 CSS
- mobile header, bottom navigation, drawer, bottom sheet
- touch 중심 interaction
- 360px 이상 작은 화면 검증

초기 이관에서는 기존 화면의 DOM·CSS·동작을 바꾸지 않는다.

### web

- PC 전용 page JSX와 CSS
- web header, navigation, sidebar, grid
- mouse·keyboard·hover 중심 interaction
- 넓은 화면에 맞춘 정보 밀도와 배치

mobile component를 억지로 확장하지 않고 구조 차이가 크면 web component를 별도로 만든다.

### admin

- 관리자 dashboard와 운영 화면
- KPI, filter, table, chart, 위험도 표시
- 사용자 쇼핑 화면과 독립된 navigation
- 담당 C 이탈방지 화면과 `AdminLayout`

admin은 `/mobile`, `/web` 전환 대상에 포함하지 않는다.

## 5. 라우팅 제안

```text
/mobile/*  → mobile 사용자 화면
/web/*     → web 사용자 화면
/admin/*   → 관리자 화면
```

### 최초 진입

1. 사용자가 저장한 보기 모드가 있으면 그것을 우선한다.
2. 저장된 값이 없을 때만 기기 또는 viewport를 기준으로 추천 경로를 정한다.
3. 자동 판별은 최초 진입에만 사용하고 사용자의 수동 선택을 덮어쓰지 않는다.

### 수동 전환

현재 세부 경로를 유지한다.

```text
/mobile/products/10 ↔ /web/products/10
```

지원하지 않는 대응 페이지라면 각 영역의 Home으로 이동하고 사용자에게 안내한다.

## 6. Component 분리 기준

다음 질문 중 하나라도 `예`이면 mobile/web component를 분리한다.

- DOM 구조가 크게 다른가?
- navigation 방식이 다른가?
- mobile은 touch, web은 hover처럼 interaction이 다른가?
- 하나의 component에 platform 조건문이 계속 늘어나는가?
- 한쪽 수정이 다른 쪽의 시각 회귀를 자주 만드는가?

예:

```text
MobileProductCard
WebProductCard
MobileHeader
WebHeader
```

반대로 역할·구조·상태가 같고 크기 차이만 있으면 공통 component의 명시적인 variant로 처리할 수 있다.
